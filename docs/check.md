## テーマ 1: 認証・アカウント・初期セットアップに関する不足事項

### 1.1 初回ログイン情報（初期ユーザー名・パスワード）がドキュメントに未記載
- **現状の課題**:
  - `README.md` にはログイン機能があることや RBAC（ロールベースアクセス制御）が記載されていたが、**「初期ユーザー名は何か」「初期パスワードは何か」が一切書かれていなかった**。
  - 初めてシステムを起動したユーザーがブラウザで `http://localhost:8080` を開いても、何を入力してログインすればよいか分からず利用を開始できない状態であった。
- **実装の実態**:
  - `data/config.toml` に初期設定が自動生成される：
    - `admin` ユーザー用パスワード: `admin_password = 'admin'`
    - `user` ユーザー用パスワード: `user_password = 'user'`
    - CLI・復号用マスターパスワード: `masterpassword = 'password'`
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [README.md](../README.md)「0. 初期ログイン情報とセットアップ時の注意事項」および「設定ファイル (`data/config.toml`)」
    - [docs/security_and_roles.md](security_and_roles.md)「1. 初期アカウントと初期設定」
  - **対応内容**:
    - 初回起動時の管理者（`admin` / `admin`）、一般ユーザー（`user` / `user`）、マスターパスワード（`password`）を明記。
    - 初回起動後に `data/config.toml` を直接編集してパスワードを変更する手順、および変更後は HCM サーバーの再起動が必須であることを明記。

### 1.2 IPアドレス制限（`permit_ip_list`）による外部遮断・初期締め出しリスク
- **現状の課題**:
  - `data/config.toml` に `permit_ip_list = ['127.0.0.1']` がデフォルトで設定されている。
  - このため、リモートサーバー上で起動した場合や、LAN 内の別 PC からアクセスした場合、あるいは Docker コンテナ経由でアクセスした場合に、**いきなり `403 Forbidden` となり接続が遮断される**。
  - なぜ 403 になるのか、どの設定を変更すれば解除できるのかがドキュメントに説明されていなかった。
- **実装上の仕様制限**:
  - `go_src/server/routes.go` の `IPRestrictionMiddleware` は `c.Request().RemoteAddr` の IP 文字列完全一致または `net.ParseIP().Equal()` のみで判定している。
  - **CIDR 表記（例: `192.168.1.0/24`）やサブネットマスク指定には未対応**。
  - **リバースプロキシヘッダー（`X-Forwarded-For`、`X-Real-IP`）を解釈しない**ため、Nginx や Docker のブリッジネットワーク背後では `RemoteAddr` がゲートウェイ IP（`172.17.0.1` 等）になってしまい遮断される。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [docs/security_and_roles.md](security_and_roles.md)「4. ネットワークとIPアドレス制限 (permit_ip_list)」
    - [docs/troubleshooting.md](troubleshooting.md)「1. エラーメッセージ別 トラブルシューティングガイド (403 Forbidden)」
  - **対応内容**:
    - `permit_ip_list` による完全一致照合の仕組みと、CIDR 未対応（個別 IP 配列指定）である仕様を明記。
    - Docker / リバースプロキシ配下での接続元 IP 判定仕様（コンテナゲートウェイ IP 登録による回避策）および、クライアント IP 追加後のサーバー再起動手順を詳細に解説。

### 1.3 サーバー再起動時の全セッション強制失効（セッションの揮発性）
- **現状の課題**:
  - サーバーを再起動すると、ログイン中だったブラウザが突然ログアウトされ、API リクエストが 401 になるが、この挙動が未記載であった。
- **実装の実態**:
  - `go_src/server/routes.go` の `sessionSecret`（HMAC-SHA256署名用秘密鍵）がプログラム起動時の `init()` でメモリ上に `rand.Read(32)` で毎回ランダム生成されている。
  - 秘密鍵がディスクに永続化されていないため、プロセスが再起動するたびに過去に発行したすべての Cookie（`session_token`）が無効化される。
- **対応結果・反映先**:
  - ℹ️ **仕様明記完了**
  - **反映先**:
    - [docs/security_and_roles.md](security_and_roles.md)「5.1 サーバー再起動時のセッション失効（仕様）」
  - **対応内容**:
    - サーバー再起動時に全セッションが強制切断されるのは、揮発性シークレットによる意図したセキュリティ仕様（残存セッションの全破棄）であることを明記。
    - 運用上の注意点として「サーバーメンテナンス・設定変更再起動の際はブラウザの再ログインが必要になる」旨を説明。

### 1.4 管理者（admin）と一般ユーザー（user）の権限差異が一覧化されていない

- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [docs/security_and_roles.md](security_and_roles.md)「2. ロール・権限マトリクス (Admin vs User)」
    - [README.md](../README.md)「7. ロールベースアクセス制御 (RBAC) & セッション認証」
  - **対応内容**:
    - 全 API エンドポイントおよび Web UI 操作に対する詳細な権限対照表（マトリクス）を作成・掲載。
    - User ロールでもホスト一覧経由でパスワードが取得可能である実態を注記し、社内運用におけるロール付与基準のガイドラインを提供。

## テーマ 2: クレデンシャルの暗号化・セキュリティ設計とドキュメントの乖離

### 2.1 「暗号化保管」表記と平文保存（TOML）の乖離
- **現状の課題**:
  - ドキュメント上では「マスターパスワードで暗号化保管されたホスト個別パスワード」「復号された対象ノードのログインパスワードを取得」といった表現が使われていた。
  - しかし実際のコード（`data/host_credentials.toml` および `data/config.toml`）では、**パスワード文字列がディスク上に平文（Plaintext）で保存されている**。
- **実装の実態**:
  - `data/host_credentials.toml`: `password = 'v3ryS3cur3_web_prod_2026'`
  - `data/config.toml`: `masterpassword = 'password'`
  - `sshFzfHandler`（`POST /api/ssh-fzf`）は、リクエストで送られた `masterpassword` が `config.toml` の `masterpassword` 文字列と一致しているかを比較しているのみで、暗号化ブロックの復号を行っているわけではない。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [README.md](../README.md)「1. 高密度・省スペースのテーブル設計」「8. IPアドレス制限 & 専用CLIクライアント」
    - [hcm-client/README.md](../hcm-client/README.md)
    - [docs/security_and_roles.md](security_and_roles.md)「3. クレデンシャル管理とファイルセキュリティ」
  - **対応内容**:
    - ドキュメント内の「暗号化保管」「復号」という表現を「マスターパスワード照合による開示ゲート制御」に全面修正。
    - 保存先がプレーンテキスト（TOML）であることを明記し、ファイルシステムのパーミッション設定（`chmod 600 data/*.toml`、`chmod 700 data`）および OS ディスク暗号化（LUKS / BitLocker）の適用を必須推奨事項として解説。

### 2.2 マスターパスワードの役割と変更時の影響
- **現状の課題**:

  - ただし、マスターパスワードを変更した直後から、すべての `hcm-client` 利用者は新しいマスターパスワードを入力しなければ接続できなくなる。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:

  - **対応内容**:
    - マスターパスワード変更手順（`data/config.toml` の `masterpassword` 変更とサーバー再起動）を記載。
    - 既存データへの暗号学的破壊リスクはないが、利用中の全クライアントへの周知が必要である運用ルールを明記。
    - 設定キー名が `master_password` ではなく `masterpassword`（アンダースコアなし）である注意点も併せて強調。

- **対応結果・反映先**:

## テーマ 4: Mutual TLS (mTLS) および証明書運用の補足が必要な事項

### 4.1 CA 更新（ローテーション）時のサーバー再起動要否
- **現状の課題**:
  - `./cert/create_certs.sh` を実行すると新 CA と新証明書が生成されることは書かれていたが、**実行後にサーバープロセスの再起動が必須であること** が強調されていなかった。
- **実態**:
  - サーバーの TLS 設定（`tlsConfig.Certificates`, `tlsConfig.ClientCAs`）はサーバー起動時にメモリにロードされる。
  - `create_certs.sh` を実行しただけでは、メモリ上のリスナーは旧 CA のままであり、再起動するまで新証明書は反映されない。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [docs/mutual_tls.md](mutual_tls.md)「3.1 Root CA およびサーバー・クライアント証明書の新規発行」の `[!IMPORTANT]` アラート
  - **対応内容**:
    - `./cert/create_certs.sh` 実行後は「**必ず HCM サーバープロセスを再起動すること**」を重要警告として追加。再起動を行わないと新クライアントがハンドシェイクエラーになる理由を解説。

---

### 4.2 CRL（証明書失効リスト）による失効の不可逆性
- **現状の課題**:
  - `./cert/revoke_cert.sh` でクライアント証明書を失効できるが、「誤って失効した場合に失効を取り消す（Unrevoke）方法」が記載されていなかった。
- **実態**:
  - CRL は不可逆的なリストであり、現行の `crl_tool.go` には失効解除（Unrevoke）機能はない。
  - 再度クライアントを使えるようにするには、新しいクライアント証明書を発行するか、証明書一式（CA・証明書・CRL）を再初期化する必要がある。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [docs/mutual_tls.md](mutual_tls.md)「4.3 失効の不可逆性と復旧（Unrevoke 不可）」
  - **対応内容**:
    - CRL 失効は取り消しができない不可逆操作である旨を明記。
    - 誤失効時または再認可時のリカバリフロー（新規クライアント証明書発行、または `./cert/create_certs.sh` による全環境再初期化）をステップ順に案内。

---

### 4.3 本番ドメインおよびパブリック証明書の適用手順
- **現状の課題**:
  - ドキュメントがローカル環境（`localhost`, `127.0.0.1`, 自己署名 CA `MyLocalSSHCA`）前提で書かれており、本番サーバー（例: `hcm.mycompany.com`）や外部パブリック認証局（Let's Encrypt 等）の証明書を適用する方法が不明であった。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [docs/mutual_tls.md](mutual_tls.md)「7.2 本番ドメイン・パブリック証明書との組み合わせ運用」
  - **対応内容**:
    - サーバー証明書（`cert/cert.pem`, `cert/key.pem`）を Let's Encrypt 等の公的証明書に差し替えつつ、mTLS クライアント検証（`cert/cacert.pem`）にはプライベート Root CA を維持するハイブリッド運用手順を記載。

---

### 4.4 リバースプロキシ（Nginx / ALB / Cloudflare 等）背後での mTLS 終端問題
- **現状の課題**:
  - 多くの本番環境では前段に Nginx やロードバランサを配置するが、リバースプロキシで TLS を終端すると **サーバーにクライアント証明書が届かなくなる**。
- **対応結果・反映先**:
  - ✅ **対応完了**
  - **反映先**:
    - [docs/mutual_tls.md](mutual_tls.md)「7.1 リバースプロキシ（Nginx, ALB等）背後での mTLS 終端問題」
  - **対応内容**:
    - mTLS を維持するためには、前段プロキシで L4 TCP パススルー（SSL passthrough）を使用し、暗号化パケットをそのまま HCM サーバーに到達させる必要がある要件を明記。
