# Mutual TLS (mTLS) 技術仕様書 & 運用設計ガイド

本書では、本プロジェクト（`host-credential-manager-go` および `hcm-client`）における **Mutual TLS (双方向TLS認証)** の技術概要、採用しているアーキテクチャ、サーバー証明書/CA更新時の旧クライアント自動失効、ならびに **CRL（証明書失効リスト）によるクライアント無効化と再ダウンロードによる復旧の仕組み** について解説します。

---

## 1. Mutual TLS (mTLS) に関する基礎技術

### 1.1 通常の TLS と Mutual TLS (mTLS) の違い

一般的な Web 通信（一方向 TLS）と mTLS（双方向 TLS）の最大の違いは、**「クライアント側も自身の身元を証明する電子証明書をサーバーへ提示するかどうか」** にあります。

```
【一般的な一方向 TLS】
Client ---------------- (1) 接続要求 ----------------> Server
Client <---------- (2) サーバー証明書の提示 ----------- Server
Client (サーバー証明書をCAで検証)
Client ---------------- (3) 暗号化セッション確立 ------> Server
※ クライアントの身元はアプリケーション層（ID/パスワード、Cookie、APIトークン等）で確認する。

【Mutual TLS (mTLS / 双方向TLS)】
Client ---------------- (1) 接続要求 ----------------> Server
Client <---------- (2) サーバー証明書 ----------------- Server
       <---------- (3) クライアント証明書要求 --------- Server (CertificateRequest)
Client (サーバー証明書をCAで検証)
Client ---------- (4) クライアント証明書の提示 -------> Server (Client Certificate)
Client ---------- (5) 秘密鍵所有の証明 ---------------> Server (CertificateVerify)
                                                Server (クライアント証明書を信頼CAで検証 & CRL検査)
Client <============== (6) 双方向認証済みTLSセッション ============> Server
```

### 1.2 mTLS のメリット
1. **ネットワーク層/トランスポート層での確実なアクセス制御**:
   - HTTP リクエストをパースする前の TLS ハンドシェイク段階で不正なクライアントを切断できるため、アプリケーション層の脆弱性攻撃やブルートフォース攻撃から根本的に保護されます。
2. **中間者攻撃 (MITM)・なりすましの完全防止**:
   - クライアント側・サーバー側の双方が信頼する CA の署名と秘密鍵を検証し合うため、通信経路上での盗聴や改ざん、なりすましが不可能です。
3. **パスワードやトークンの漏洩リスク低減**:
   - 認証が公開鍵暗号（秘密鍵によるデジタル署名）に基づくため、平文のパスワードや Bearer トークンが盗聴されて悪用されるリスクがありません。

## 2. 本アプリケーションで採用している設計と仕組み

本システムでは、**「ブラウザからの管理画面アクセス（Web UI）の利便性」** と **「CLI クライアント (`hcm-client`) からの安全な自動接続」** を両立させるため、以下の独自設計を採用しています。

```
                                  +-------------------------------------------------+
                                  |            Host Credential Manager              |
                                  |                    (Server)                     |
                                  |                                                 |
                                  |  TLS Listener (Port 8080)                       |
                                  |  ClientAuth: tls.VerifyClientCertIfGiven         |
                                  +-----------------------+-------------------------+
                                                          |
                      +-----------------------------------+-----------------------------------+
                      |                                                                       |
                      v                                                                       v
     【Web ブラウザ / Web UI】                                               【hcm-client (CLI)】
     - クライアント証明書なし                                                    - 埋め込みクライアント証明書あり
     - セッション認証 / パスワード認証                                           - mTLS 必須エンドポイントへアクセス
                      |                                                                       |
                      v                                                                       v
       /api/login, /api/hostlist,                                           /api/ssh-fzf, /api/targets
       /api/client/download                                                                   |
                      |                                                                       |
                      v                                                                       v
                 [ 200 OK ]                                              [ RequireClientCertMiddleware ]
                                                                                              |
                                                                    +-------------------------+-------------------------+
                                                                    |                                                   |
                                                                    v                                                   v
                                                            証明書あり・有効                                    証明書なし / CRL失効
                                                                    |                                                   |
                                                                    v                                                   v
                                                               [ 200 OK ]                                        [ 401 Unauthorized ]
```

### 2.1 デュアルモード TLS (`tls.VerifyClientCertIfGiven` + エンドポイント保護)

- **課題**:
  サーバー全体で `ClientAuth: tls.RequireAndVerifyClientCert` を有効にすると、Google Chrome や Firefox などの Web ブラウザから Web UI を開く際にもブラウザにクライアント証明書をインポートしなければ接続できなくなり、UX が極めて低下します。
- **解決策**:
  1. サーバーの TLS 設定（`main.go` / `go_src/server/tls.go`）では `ClientAuth: tls.VerifyClientCertIfGiven` を採用。
     - クライアント証明書が提示されない場合でも TLS ハンドシェイク自体は成功させます（ブラウザからのアクセスを許可）。
  2. CLI クライアント専用のエンドポイント（`/api/ssh-fzf`, `/api/targets`）に **`RequireClientCertMiddleware`** を配置。
     - リクエストの `c.Request().TLS.PeerCertificates` をチェックし、有効なクライアント証明書が存在しないアクセスを `401 Unauthorized` で拒否します。
  3. Web UI 側の機能（ホスト一覧表示、パスワード自動生成、`hcm-client.tgz` のダウンロード等）は、Web ログイン認証（`RequireAuth("admin", "user")`）で保護し、クライアント証明書なしで利用可能です。

### 2.2 単一共有クライアント証明書 & ワンバイナリ運用

- 多数のユーザーやマシンごとに個別の証明書を発行・配布する運用はコストが高くなります。
- 本システムでは、**全クライアント共通の共有クライアント証明書（`client_cert.pem`, `client_key.pem`）** を 1 ペア発行し、Go の `//go:embed` 機能によって `hcm-client` バイナリの内部に直接埋め込んでいます。
- これにより、利用者は証明書ファイルや秘密鍵ファイルを意識することなく、配布された単一バイナリを実行するだけで自動的に mTLS 認証が行われます。

## 3. CA更新による旧クライアント自動失効の仕組み

本システムの重要な要件である **「HCM サーバーの証明書/CAを更新した際に、古い hcm-client を一括して接続不可にする」** 仕組みは、TLS のトラストアンカー（信頼点）の更新によって実現されています。

### 3.1 動作フロー
1. 管理者がサーバー側で `./cert/create_certs.sh` を実行します。
2. これにより、新しい秘密鍵と新しいシリアル番号を持つ **新しい Root CA (`cacert.pem`, `cakey.pem`)** が生成され、同時にその新 CA で署名された新しいサーバー証明書および新しいクライアント証明書が発行されます。
3. **サーバープロセスを再起動します**。
   > [!IMPORTANT]
   > **サーバーの再起動が必須です**:
   > サーバーの TLS リスナーは起動時に `cert/cacert.pem` を読み込んで `ClientCAs` をメモリ上に構成します。そのため、スクリプト実行後は必ず HCM サーバープロセスを再起動してください。再起動によってメモリ上の `ClientCAs` が新 Root CA に切り替わります。
4. **旧 `hcm-client` の接続試行**:
   - 旧バイナリに埋め込まれているクライアント証明書は「旧 Root CA」によって署名されています。
   - サーバー側は提示されたクライアント証明書の署名チェーンを検証しますが、旧 CA は現在の `ClientCAs` に含まれていません。
   - 結果として、**TLS ハンドシェイクの時点でサーバーが即座にエラーを返し、接続が切断されます**：
     ```text
     remote error: tls: unknown certificate authority
     ```
   - 仮にクライアント側で `--insecure`（サーバー証明書検証のスキップ）を指定して実行したとしても、**サーバー側が行うクライアント証明書の検証を回避することは原理的に不可能** です。

## 4. CRL（証明書失効リスト）による特定証明書の無効化

CA 自体を更新することなく、特定のクライアント証明書を即座に無効化（Revoke）したい場合は、**CRL (Certificate Revocation List)** を使用します。

### 4.1 CRL の仕組み
- CRL は、有効期限内であるものの無効化された証明書のシリアル番号、失効日時、失効理由が記録されたリストです。
- Root CA の秘密鍵によって電子署名されており、改ざんが防止されています。

### 4.2 本システムにおける CRL 実装
- **Pure Go 製ツール [`cert/crl_tool.go`](../cert/crl_tool.go)**:
  - OpenSSL の複雑な `index.txt` や設定ファイルに依存せず、Go の `crypto/x509` パッケージを用いて RFC 5280 準拠の X.509 v2 CRL（`cert/crl.pem`）を生成・更新します。
- **失効スクリプト [`cert/revoke_cert.sh`](../cert/revoke_cert.sh)**:
  - `./cert/revoke_cert.sh cert/client_cert.pem` を実行するだけで、指定した証明書のシリアル番号を `cert/crl.pem` に追記・署名更新します。

### 4.3 リアルタイムでの接続遮断
サーバー側では、2重の防壁によって失効証明書を排除します：
1. **TLS レベル（`tlsConfig.VerifyConnection`）**:
   - TLS ハンドシェイク完了直前に `cert/crl.pem` を読み込み、クライアントから提示された証明書のシリアル番号が失効リストに存在するか照合します。
   - 失効されている場合はエラーを返し、TLS ハンドシェイクを中断します（クライアント側には `tls: bad certificate` アラートが送信されます）。
2. **アプリケーション層（`RequireClientCertMiddleware`）**:
   - 万が一ハンドシェイクを通過した場合でも、エンドポイント受信時にミドルウェアが `IsCertRevoked()` を実行し、`401 Unauthorized`（`Client certificate has been revoked`）を返します。
- サーバー再起動を行わなくても、`crl.pem` が更新された瞬間に次のリクエストから即座に遮断されます。

### 4.4 失効の不可逆性と再有効化手順
- CRL による失効は原則として不可逆的です。`crl_tool.go` には失効解除（Unrevoke）機能は意図して設けていません。
- もし誤って失効させた、あるいは再度利用を再開したい場合は、**`./cert/create_certs.sh` を実行して CA・証明書・CRL を一括再初期化** してください。これにより CRL が空にリセットされ、新しく生成されたクライアント証明書で再開できます。

## 5. Web UI (Manager) からの再ダウンロードによる復旧の仕組み

CA 更新や CRL 失効によって旧バイナリが使えなくなった場合、利用者が **「Web UI から新しいクライアントをダウンロードするだけ」** で復旧できる仕組みが組み込まれています。

```
      【利用者 / 管理者】                                                  【HCM サーバー】
              |                                                                   |
              | 1. ブラウザで Web UI にログイン (証明書不要)                           |
              |------------------------------------------------------------------>|
              |                                                                   |
              | 2. 「hcm-client.tgz」ダウンロードボタンをクリック                    |
              |------------------------------------------------------------------>|
              |                                                                   |
              |                                               3. downloadHcmClientHandler:
              |                                                  - cert/cacert.pem や client_cert.pem の
              |                                                    更新時刻(ModTime) と既存バイナリを比較
              |                                                  - CA/証明書が更新されていれば
              |                                                    hcm-client/build.sh を自動再実行！
              |                                                  - 新しい証明書をバイナリ内に自動埋め込み
              |                                                  - hcm-client.tgz として tar.gz アーカイブ
              |                                                                   |
              | 4. hcm-client.tgz (新バイナリ・新証明書一式) の受信                 |
              |<------------------------------------------------------------------|
              |                                                                   |
              | 5. アーカイブを解凍して実行                                       |
              |    ./run.sh または ./hcm-client                                   |
              |------------------------------------------------------------------>| [ mTLS 認証成功！ ]
```

### 5.1 自動ビルド追従ロジック (`downloadHcmClientHandler`)
[`go_src/server/routes.go`](../go_src/server/routes.go) の `downloadHcmClientHandler` は以下の処理を行います：
1. `hcm-client/built/hcm-client` の存在を確認。
2. サーバー上の `cert/cacert.pem` または `cert/client_cert.pem` の更新日時（ModTime）が、ビルド済みバイナリの更新日時よりも新しいかどうかを判定。
3. 新しい証明書が存在する場合、自動的に `hcm-client/build.sh` を呼び出して再コンパイルを実行。
4. 新しい Root CA と新しいクライアント証明書が埋め込まれたバイナリをパッケージングし、ブラウザへストリーミング送信。

これにより、管理者がサーバー側で証明書をローテーションした場合でも、エンドユーザーは管理画面から最新のパッケージを再ダウンロードするだけで、手動コンパイルや証明書の配置作業を一切行うことなく最新環境へ復帰できます。

## 6. 管理者向け運用コマンドリファレンス

### 証明書・CA・CRL の新規生成・ローテーション
```bash
# Root CA, サーバー証明書, クライアント証明書, 初期CRLを一括生成
./cert/create_certs.sh
```

### クライアント証明書の失効 (CRL更新)
```bash
# 共有クライアント証明書を失効リストに登録
./cert/revoke_cert.sh cert/client_cert.pem
```

### 証明書の失効確認
```bash
# 対象の証明書が失効されているかどうかを確認
go run cert/crl_tool.go check cert/client_cert.pem
# 戻り値: VALID (未失効: exit 0) / REVOKED (失効済み: exit 2)
```

### クライアントのビルドと動作確認
```bash
# クライアントバイナリのビルド
./hcm-client/build.sh

# 登録ターゲット一覧取得（mTLS 疎通確認テスト）
./hcm-client/built/hcm-client --list
```

## 7. 本番公開・リバースプロキシ連携時の注意事項

### 7.1 リバースプロキシ（Nginx / ALB 等）背後での mTLS 終端問題
本番環境で Nginx や AWS ALB 等のリバースプロキシを前段に置く場合、一般的な L7 リバースプロキシ（HTTP/HTTPS プロキシ）で TLS を終端すると、**クライアント証明書が HCM サーバーへ渡らなくなり、mTLS 認証がすべて失敗します**。
- **解決策**:
  - 前段のロードバランサ / プロキシは **L4（TCP / SSL パススルー）** で設定し、暗号化パケットをそのまま HCM サーバーのポート 8080 へ転送してください。

### 7.2 外部パブリック認証局（Let's Encrypt 等）との併用
- サーバーの Web UI にブラウザでアクセスする際にオレオレ証明書の警告を出さないよう、Let's Encrypt などのパブリック証明書を使用する場合：
  - `cert/cert.pem` および `cert/key.pem` をドメインの正規証明書に差し替えます。
  - mTLS 用の Root CA（`cert/cacert.pem`）およびクライアント証明書（`cert/client_cert.pem`）は、HCM のプライベート CA のものをそのまま併用可能です（サーバー証明書の CA とクライアント証明書の CA は異なっていても問題ありません）。
