# セキュリティ・アカウント・ロール権限 仕様書 (`security_and_roles.md`)

本書では、Host Credential Manager (HCM) におけるアカウント体系、初期認証情報、ロール権限（Admin / User）の違い、認証情報の保存仕様とファイルシステム保護、マスターパスワードの仕様、および IP アドレス制限の詳細について解説します。

---

## 1. 初期アカウントと初回セットアップ

### 1.1 初期認証情報一覧
HCM は初回起動時、`data/config.toml` が存在しない場合に以下のデフォルト設定でファイルを自動生成します：

| アカウント / 項目 | 初期値 | 役割・用途 |
| :--- | :--- | :--- |
| **管理者ユーザー (`admin`)** | `admin` | Web UI 管理者ログイン（全操作・編集・削除・インポート・エクスポート可能） |
| **一般ユーザー (`user`)** | `user` | Web UI 一般ログイン（ホスト一覧閲覧、パスワード生成、クライアントDLのみ） |
| **マスターパスワード (`masterpassword`)** | `password` | CLI (`hcm-client`) および API (`POST /api/ssh-fzf`) 経由で対象ホストのパスワードを取得する際の照合用共通鍵 |
| **許可IPリスト (`permit_ip_list`)** | `['127.0.0.1']` | サーバーへのアクセスを許可するクライアント IP アドレス |

> [!CAUTION]
> **本番運用前の必須設定**:
> 初期値（`admin` / `user` / `password`）のまま運用すると、同一ネットワークから不正アクセスを受ける重大なセキュリティリスクとなります。**初回起動後、直ちに `data/config.toml` を編集して強力なパスワードに変更し、サーバーを再起動してください。**

### 1.2 パスワード変更手順
1. サーバープロセスを停止します（または編集後に再起動します）。
2. `data/config.toml` をエディタで開きます：
   ```toml
   permit_ip_list = ['127.0.0.1', '192.168.1.50']
   masterpassword = 'YourStrongMasterPasswordHere!'
   admin_password = 'YourStrongAdminPasswordHere!'
   user_password = 'YourStrongUserPasswordHere!'
   ```
3. サーバーを起動（再起動）します。
   - Web UI からログインする際は、新しい `admin_password` または `user_password` を使用します。
   - `hcm-client` 利用者には、新しい `masterpassword` を周知します。

## 2. ロール権限マトリクス (Admin vs User)

本システムはロールベースアクセス制御 (RBAC) を採用しています。ログイン時に発行される Cookie（`session_token`）に基づき、各 API エンドポイントへのアクセス権が判定されます。

### 2.1 権限対比表

| 機能・操作 | エンドポイント | Admin | User | 未ログイン |
| :--- | :--- | :---: | :---: | :---: |
| **Web ログイン** | `POST /api/login` | ◯ | ◯ | ◯ |
| **Web ログアウト** | `POST /api/logout` | ◯ | ◯ | ◯ |
| **ログイン状態・ロール確認** | `GET /api/role` | ◯ | ◯ | ◯ (role: null) |
| **ホスト一覧 & 認証情報の閲覧** | `GET /api/hostlist` | ◯ | ◯ | ✕ (401) |
| **パスワード自動生成ツール** | `GET /api/password/generate` | ◯ | ◯ | ✕ (401) |
| **クライアントパッケージDL** | `GET /api/client/download` | ◯ | ◯ | ✕ (401) |
| **ホスト新規登録** | `POST /api/hostlist` | ◯ | ✕ (403) | ✕ (401) |
| **ホスト情報・認証情報の更新** | `PUT /api/hostlist/:id` | ◯ | ✕ (403) | ✕ (401) |
| **ホスト削除** | `DELETE /api/hostlist/:id` | ◯ | ✕ (403) | ✕ (401) |
| **CSV インポート** | `POST /api/hostlist/import` | ◯ | ✕ (403) | ✕ (401) |
| **CSV エクスポート** | `GET /api/hostlist/export` | ◯ | ✕ (403) | ✕ (401) |
| **CLI ターゲット一覧取得** | `GET /api/ssh-fzf` | ✕ (mTLS必須) | ✕ (mTLS必須) | ✕ (401) |
| **CLI パスワード取得** | `POST /api/ssh-fzf` | ✕ (mTLS必須) | ✕ (mTLS必須) | ✕ (401) |

> [!IMPORTANT]
> **User ロールに関する重要な注意点**:
> `GET /api/hostlist` には各ホストのログインユーザー名およびパスワード（`userlist`）が含まれます。そのため、現行の仕様では **User ロールでログインしたユーザーも画面上または API レスポンス経由でホストのパスワードを閲覧・コピーできます**。
> User ロールに制限されているのは「ホストの新規作成・変更・削除」および「CSV のインポート/エクスポート」であり、閲覧権限の分離（特定ホストのみ閲覧可能にする等）は行われません。

## 3. クレデンシャル（パスワード）の保存仕様とファイルシステム保護

### 3.1 データの保存形態（平文 TOML）
本システムでは、高速なファイルベース運用を実現するため、以下のファイルに認証情報を平文（Plaintext）で保存しています：
- `data/config.toml`: システムパスワード、マスターパスワード
- `data/host_credentials.toml`: 各ターゲットホストのログインユーザー名、パスワード

`hcm-client` や `POST /api/ssh-fzf` が要求する「マスターパスワード」は、暗号化ブロックの復号鍵ではなく、**「サーバーに保管されている平文パスワードを取り出すための照合用ゲートウェイパスワード（共有シークレット）」** として動作します。

### 3.2 必須のファイルシステム保護策
パスワードが平文で保存されているため、**サーバーホスト自体のファイルアクセス権限を厳格に管理することが極めて重要** です。

```bash
# data ディレクトリのアクセス権を所有者のみに制限
chmod 700 data

# 設定ファイルおよび認証情報ファイルのアクセス権を厳格化
chmod 600 data/*.toml

# 証明書の秘密鍵も同様に所有者のみに制限
chmod 600 cert/*key.pem
```

#### 推奨される本番運用環境:
1. **ディスク全体の暗号化**:
   - サーバーのストレージに LUKS (Linux Unified Key Setup) やクラウドプロバイダの暗号化ボリューム（AWS EBS 暗号化、GCP CMEK 等）を適用してください。
2. **最小権限ユーザーでのデーモン実行**:
   - `root` ユーザーではなく、専用の非特権ユーザー（例: `hcm` ユーザー）を作成してサービスを実行してください。

## 4. IP アドレス制限 (`permit_ip_list`) の仕様と注意点

### 4.1 動作仕様
`go_src/server/routes.go` の `IPRestrictionMiddleware` は、すべての HTTP / HTTPS リクエストに対してアクセス元 IP アドレスの検証を行います。

```toml
# data/config.toml
permit_ip_list = [
  '127.0.0.1',
  '192.168.10.15',
  '10.0.5.21'
]
```

### 4.2 制限事項とトラブルシューティング
1. **CIDR 表記は未対応**:
   - `192.168.1.0/24` のようなサブネット指定はサポートされていません。完全一致の個別 IP アドレスを配列で列挙してください。
2. **IPv6 アドレスの扱い**:
   - ローカルホストから IPv6 で接続された場合（`[::1]`）、`permit_ip_list` に `127.0.0.1` が含まれていれば自動的にループバックとして許可されます。外部からの IPv6 接続を許可する場合は、該当の IPv6 アドレスを記載してください。
3. **Docker / リバースプロキシ環境での 403 エラー**:
   - 本ミドルウェアは `c.Request().RemoteAddr`（TCP コネクションの送信元 IP）を直接参照します。
   - Nginx 等のリバースプロキシ背後や Docker の NAT ネットワーク経由で配置した場合、接続元 IP がプロキシやゲートウェイ（例: `172.17.0.1`）として認識され、`403 Forbidden` が返される原因となります。
   - **対処法**: プロキシまたはコンテナゲートウェイの IP アドレスを `permit_ip_list` に追加してください。

## 5. セッション管理と監査ログ

### 5.1 セッション Cookie の仕様
- ログイン成功時、ブラウザに `session_token` という名前の HttpOnly Cookie が発行されます。
- 有効期限は発行から **24 時間** です。
- **セッション秘密鍵の揮発性**:
  - セッション検証用の HMAC 秘密鍵はサーバー起動時にメモリ上にランダム生成されます。
  - **サーバーが再起動すると、過去に発行されたすべてのセッションが無効化され、全クライアントが再ログインを要求されます**。これは意図したセキュリティ仕様です。

### 5.2 監査ログ (Audit Log) について
- 現行バージョンでは、Echo 標準の HTTP アクセスログ（IP、メソッド、パス、レスポンスコード、処理時間）が標準出力に出力されます。
- 「誰が・いつ・どのホストのパスワードを取得したか」という詳細な監査証跡（Audit Trail）機能は現行バージョンでは専用ログとして記録されません。必要に応じてリバースプロキシ側のログや OS の syslog と連携して記録を保全してください。
